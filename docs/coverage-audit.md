# 取りこぼしの監査と「利用者とともに育つ」設計

開始: 2026-10-29。目的は、分類と地域の取りこぼしを、利用者が報告する前に見つけること。PHILOSOPHY.md・PRODUCT.md の原則（データは端末内、一次情報だけ、選定の基準を説明できる）は変えない。

## きっかけ

2026-10-29、利用者が「生成AI × カナダ」がほぼ空だと気づいた。カナダ首相府の Cohere への投資の発表は取得済みだったが「政治」だけで、Cohere 自身の PR Newswire の発表は「米国」に入っていた。記事が**ない**ことは利用者の画面に現れないため、規則の穴は報告されるまで残る。情報源を増やすほど、この種の穴は増える。

## いま自動で行うこと（実装済み）

`src/coverageAudit.ts`（判定）と `scripts/coverage-audit.ts`（実行）。読むのは公開データ（`news.json`・`sources.json`・`meta.json`）だけで、利用者の設定・閲覧・保存した記事は読まない。報告するだけで、規則もフィードも変えない。

| 判定 | 内容 |
|---|---|
| 見出しの取りこぼし | 政府・研究機関・団体の見出しが分野（AI・ロボット・半導体・量子・計算基盤・サイバー・防衛・貿易・数学・投資額）を名指ししているのに、そのカテゴリがない記事。発信元ごとにまとめる。企業の発表は「AI 搭載」の宣伝と区別できないため、基盤モデルの名指しだけを見る |
| カテゴリ×地域 | 既定でオンの情報源で、直近7日とその前の7日を比べる。地域もカテゴリも動いているのに空の組み合わせ、前の週から 25% 以下に落ちた組み合わせ |
| 配信サービスの地域 | 説明文の日付行が示す地域と、付いている地域が違う記事（フィードごと）。日付行が短縮で消えた記事は、本文が一つの地域だけを名指ししているかを手がかりにする |
| 既定トピックの語 | `src/profile.ts` の既定トピックの語が、対応するカテゴリの規則に一致しないもの。入れない語は理由つきで `INTENTIONAL_KEYWORD_GAPS` に書く |

各候補は、いまのコードで分類し直して「未解決」と「コード側で解消済み（次の公開で反映）」に分ける。優先度は P1（10件以上、または見出しの取りこぼしがある空の組み合わせ、または前の週からゼロになった組み合わせ）・P2・P3。

- 手元: `npm run audit:coverage`（`site/data` → `data/preview/snapshot` → https://sivree.com/data の順に探す。`--data`・`--json`・`--markdown`・`--all`）。
- 公開ワークフロー（約3時間ごと）: 公開するデータに対して実行し、実行結果の要約（Step Summary）に書く。`continue-on-error` で、公開を止めない。
- `npm run operations`: `report.md` の「Coverage audit」節と `coverage.json`。終了コードには影響しない（語の一致による候補で、品質の失敗ではないため）。
- `npm run test:coverage`: 監査そのものの回帰テスト。2026-10-29 の事例（分類・地域）を見つけること、既定トピックの語が規則に入っているか理由が書いてあることを確かめる。

### 初回の結果（2026-10-29〜30、公開データ 3,740 記事）

- 首相府と PR Newswire の Cohere の発表の「生成AI」: 80fdebe で解消。公開データ（10/30 00:51 生成）で確認。
- PR Newswire の **Venture Capital と決算発表のフィードに日付行の設定がなかった**（80fdebe は別の2フィードだけ）。Cohere の発表は米国のまま、決算発表 30件が欧州・カナダの日付行なのに米国だった。両フィードに `datelineRegion` を付け、PR Newswire の全フィードに付いていることをテストで固定した。既存の記事は、取得し直されたときに直る（蓄積記事の説明文は短縮済みで日付行がないことがある）。
- 規則の語の不足: robotic・mathematicians・ランサムウェア・サイバーセキュリティ（英語の cyber security は入っていた）を追加。
- 未解決（判断が要るため残した）: 投資の規則がドル建ての金額しか見ない（欧州委員会の「€3.4 billion」が投資に入らず、投資×欧州が空）。貿易の見出しに対応するカテゴリの規則がない（日本以外）。政治×米国が前の週 33件→0件（米国務省などの取得を確かめる）。グローバル地域の多くの組み合わせが空（情報源の範囲の問題）。

## 判定の限界

- 語の一致による**候補**で、取りこぼしかどうかの最終判断ではない。修正するかは、見出しと原文を読んで決める。
- 公開前に捨てられた記事は見えない。`matchOnly` のフィード（配信サービスなど）は、どのカテゴリにも一致しない記事を取り込まないため、規則の穴で落ちた記事は公開データに残らない。次の段階として、取得時に捨てた見出しの件数と例を CI のログにだけ残す（公開しない）方法を検討する。
- 公開データの説明文は100字に短縮されているため、日付行や本文の語が消えていることがある。「いまのコードで分類し直すと」の件数は近似である。

## 自動で直してよいことと、承認が必要なこと

| 変更 | 扱い |
|---|---|
| 監査の実行・報告（手元、CI の要約、operations） | 自動 |
| 分類規則の語の追加・修正、既存フィードの属性（`datelineRegion`・`categoryByUrl` など、`feedUrl` は変えない）の修正。テストを足してブランチにコミット | 自動（push は承認後） |
| `INTENTIONAL_KEYWORD_GAPS` への追加 | 自動。ただし理由を書く。push のときに確認を受ける |
| 監査の閾値や判定語を緩めて候補を消すこと | しない（テストの期待値を緩めて完了にしないのと同じ） |
| カテゴリの意味を変える変更（新しいカテゴリ、貿易を経済に含めるなど） | 利用者の承認 |
| 情報源の追加（利用条件の確認、`since`、候補） | 利用者の承認 |
| 専門パックの内容、国際・地域の階層の一覧、既定でオンにすること | 利用者の承認（`test:feeds` が固定している） |
| `git push`・公開・Issue・外部への送信 | 利用者の承認 |

空の組み合わせを、報道機関の記事で埋めることはしない。一次情報源の範囲の限界として扱う（PRODUCT.md「範囲には限りがある」）。

## 利用者に見える差別化へ（提案。未実装、各段階に承認が必要）

「Sivree は利用者とともに育つ」を、利用者のデータを集めずに実現する。学習の材料は公開データと、利用者が自分で選んで送るものだけにする。

1. **改善の記録を公開する**（公開データだけで可能）。監査で見つけて直したことを、日付・件数・理由つきで公開ページに載せる（例: 「10/29 配信サービスの決算発表 30件の地域を日付行で決めるようにした」）。選定と分類の基準を説明できるようにする原則（PRODUCT.md 3・5）の延長で、外向けの公開なので承認が要る。
2. **端末内の手がかり**。公開の件数（カテゴリ×地域）と端末内の設定（トピック・地域）を端末の中で突き合わせ、「生成AI×カナダは今週0件。候補の情報源が N件あります」と設定の候補へ案内する。計算は端末内で、何も送らない。
3. **利用者が選んで送る報告**。記事に「分類が違う」を付け、記事の URL と利用者が選んだカテゴリだけの文面を作る。送るかどうか、どこへ送るか（メールまたは GitHub の Issue）は利用者が決め、送る内容をそのまま見せる。設定・識別子は入れない。受け取った報告は、監査の判定語かテストの事例に加え、同じ穴を自動で見つけられるようにする。
4. **端末内の個人的な補正**。利用者が自分の端末で分類の補正（例: このフィードの記事に AI があれば生成AIにも入れる）を持ち、既存のコピー・貼り付けとドライブ同期で運ぶ。補正はサーバーに集めないため、他の利用者には広がらない。これは受け入れる制約である。

行わないこと: 読んだ記事・検索・設定を集めて穴を探すこと、サーバー側の利用者プロファイル、アカウント、報道機関の記事やSNSで空の組み合わせを埋めること。

対外的な説明は、実装したことだけにする。いま言えるのは「公開データの自動監査が約3時間ごとに走り、分類・地域の取りこぼしの候補を開発者に示す」まで。1. が公開されるまで、「利用者とともに育つ」を機能として説明しない。
