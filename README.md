# Sivree（パーソナルニュースアプリ α版）

公的機関・企業などの一次情報を扱う個人用ニュースアプリのα版です。公式サイトの RSS/Atom からニュースを集め、カテゴリ別に一覧表示し、記事を開くと発信元ページから抽出した概要を表示します。

## 主要機能
- **初回の質問**: 最初の起動時に「どの国・地域の情報を受け取るか」「どの分野を柱にするか」の2問に答えます。選んだ分野だけがタブになり、地域・分野の外にある発表はすべてのタブとブリーフィングに表示しません（対象外の地域の情報源は取り込みもしません）。設定の「地域・分野」でいつでも変更でき、「初期設定に戻す」で質問からやり直せます
- **マイニュース**（最初のタブ）: 関心プロフィールに一致する記事を、関連度と新しさで並べて表示。各記事に「なぜ表示されたか」（一致した関心トピック）を表示
- 関心プロフィールは画面右上の設定ボタンから編集（トピックの追加・削除、説明文、キーワード、優先度、オン／オフ）。キーワードに加えて、説明文に内容が近い記事も表示（手元で動く埋め込みモデルを使い、外部の AI サービスは使わない）
- カテゴリタブ（すべて / 政治 / 経済 / 投資 / 安全保障 / 国際 / 社会 / テクノロジー / 生成AI / サイエンス / 文化・芸術 / イベント のうち、選んだ分野）。カテゴリごとに色分け
- 各タブで地域（日本 / カナダ / 米国 / 欧州 / グローバル）と発信元（政府・自治体 / 企業 / 研究機関 / 団体・NPO）を選択。選択はタブごとに保持
- 記事をタップすると詳細画面へ。要約と要点、本文の冒頭、「元記事を読む」ボタンを表示
- キーワード・ハッシュタグ検索、記事の共有、ダークモード

## 実行方法
```bash
npm install
npm run dev
```

設定を変える場合は `cp .env.example .env` を実行して `.env` を編集します（設定しなくても全機能が動作します）。

## 要約
要約エンジンは差し替え可能で、`.env` の `SUMMARY_PROVIDER` で選びます。

| エンジン | 内容 | 費用・依存 |
|---|---|---|
| `extractive`（既定） | 生成AIを使わず、本文を文に分けて採点し（見出しとの関連・文書内での中心性 [TextRank]・冒頭からの位置）、重要な文をそのまま抜き出す。数値や日付を含む文を「要点」にする | 費用ゼロ、外部サービス不要、オフラインで動作。本文にないことは書かない |
| `local` | 手元やオンプレミスで動かすオープンソースのモデル（Qwen、Gemma、Llama、日本語特化モデルなど）が要約を書く。Ollama / LM Studio / llama.cpp / vLLM の OpenAI 互換 API に対応 | 自前の計算資源のみ。英語記事の日本語訳もできる |
| `claude` | Claude API（`claude-opus-5-5`）が要約を書く | API 利用料。`ant auth login` または API キーが必要 |

- 要約の根拠は発信元の本文のみ（PDF 資料はテキストを取り出して使う）。会社概要・問い合わせ先・定型文は除外します。
- LLM の呼び出しに失敗した場合は、自動で抽出型の要約に切り替えます。
- LLM の誤り対策: 本文がほとんど取れない記事（リンク集のページ等）は LLM に渡さず、取得に失敗した記事は後で再試行します。LLM の出力に本文にない数値が含まれる場合、その要点は除外し、要約本文に含まれる場合は採用しません。ただし、数値の取り違え（1株利益を純利益と書く等）や本文にない解釈までは検出できません。
- `local` の検証結果（2026年10月、M2 / メモリ 8GB の Mac、`qwen3:4b`）: 抽出型より記事の核心をよく捉え、英語記事も日本語で要約できる一方、1件 30〜75 秒かかり、小さな誤り（指標の取り違え、本文にない補足、誤字）が見られました。実用には、より大きなモデルを GPU サーバー等で動かすことを推奨します。
- 作成した要約は `data/summaries.json` に保存し、エンジンを切り替えた場合は新しいエンジンで作り直します。
- 抽出型は軽いため、新着記事（最新80件）を自動で事前に要約し、一覧のカードにも表示します。LLM の場合は `AUTO_SUMMARY_LIMIT` の件数まで。
- 画面上では、抽出型は「要約（本文から抜粋）」、LLM は「AI要約（モデル名）」と区別して表示します。

**情報源の選択**: 設定画面の「情報源」で、情報源ごと（または種類ごと）にオン・オフを切り替えられます。オフにした情報源は、すべてのタブ・ブリーフィング・関連記事に表示されません。利用者全員がオフにした情報源は、取得も保存もしません（オンに戻すと、次の表示で取り込み直します。それまでの蓄積分は残りません）。設定は `excludedSources`（情報源 ID の一覧）としてプロフィールに保存し、一覧は `GET /api/sources` で取得できます。

上記に加え、見出し・説明文に含まれる語で次のように分類します（`src/newsPipeline.ts` の `CATEGORY_RULES`）。
- 企業の発表のうち、提携・買収・決算・業績修正・上場・工場や生産・値上げ・事業終了・経営体制の変更・倒産、および事故や不祥事（リコール、不正アクセスや情報漏えいの報告、システム障害など）に関するものは **経済** に入れる（英語の発表も同様: acquisition, earnings, IPO, recall, data breach など）
- 「資金調達」「シリーズA」「国内投資」などを含む記事は **投資** に入れ、経済からは外す
- 「生成AI」「LLM」「AIエージェント」などを含む記事は **生成AI** にも表示する
- 日本の情報源で「首脳」「外相」「国連」などを含む記事は **国際・日本** にも表示する

公的機関の発表が経済カテゴリの大半を占めないよう、次のように制限しています。
- 日本銀行・財務省・金融庁は1日6件、経済産業省は8件まで（FRB・ECB は6件まで）
- 入札・落札結果、国庫短期証券の発行、職員募集、説明会などの定型的なお知らせは除外
- 企業発表のうち、法律事務所による集団訴訟の勧誘、ウェビナー・セミナー告知、翻訳版（英語以外の PR Newswire 配信）は除外

## マイニュース（パーソナライズ）
- 関心トピックごとに日本語・英語のキーワードを持ち、記事の見出し・説明文・要約に含まれるかで一致を判定します。見出しで一致した記事は、本文で触れているだけの記事より高く評価します。
- さらに、トピックの**説明文**と記事の内容が近いかを、手元で動く小さな埋め込みモデルで判定します（下記）。キーワードを含まない記事（例: 「AI」と書かずに LLM の研究を扱う発表）も拾えます。画面では、内容の近さで一致した関心に「≈」を付けます。
- トピックには条件を付けられます: 地域の限定（例: 米国・EU のテック政策）、発信元の種類の限定（企業ブログを除く等）、両方の語を含む場合のみ（例: 日本×カナダ）、特定の発信元は常に対象（例: ウォータールー地域の市・リージョン）、単独では表示せず他の関心と重なる記事を上位にする（例: 提携・資金調達）。
- 並び順は「一致したトピックの優先度 × 一致の強さ の合計 × 新しさ（3日で半分）」です。

### 内容の近さによる判定（埋め込みモデル）
生成モデルや外部の AI サービスは使わず、文をベクトルにするだけの小さなオープンソースのモデルを、このサーバーと同じ環境（またはオンプレミス）で動かします。OpenAI 互換の `/v1/embeddings` を使うため、Ollama・llama.cpp・vLLM・Text Embeddings Inference のどれでも動きます。

```bash
brew install ollama && ollama serve   # 別のターミナルで
ollama pull embeddinggemma:300m       # 約 620MB
```

- 記事は取得後に裏でベクトル化し、`data/embeddings.json` に保存します（514件で約16秒、M2 / 8GB）。
- 埋め込みモデルに接続できない場合は、5分おきに再接続を試しながらキーワードだけで判定します。
- 設定: `EMBEDDING_MODEL`（既定 `embeddinggemma:300m`、`off` で無効）、`EMBEDDING_URL`（既定 `http://localhost:11434/v1`）、`EMBEDDING_THRESHOLD`（一致とみなす類似度。モデルごとの既定値は `src/embeddings.ts`）、`EMBEDDING_API_KEY`。
- 地名のトピック（ウォータールー周辺・オンタリオ州・日本×カナダ）は、意味の近さでは判定しにくいため説明文を空にしてキーワードだけで判定しています。

モデルの比較（2026年10月11日、収集済みの記事 259件に手作業で正解を付けて評価。数値は AUC、括弧内は最良のしきい値での F1）:

| モデル | ライセンス | 生成AI | Physical AI | 数学・新発見 | 速度 |
|---|---|---|---|---|---|
| embeddinggemma（採用） | Gemma 利用規約 | 0.986 (0.83) | 0.999 (0.96) | 0.909 (0.75) | 約 100ms/件 |
| qwen3-embedding:0.6b | Apache 2.0 | 0.970 (0.78) | 0.994 (0.87) | 0.866 (0.43) | 約 80ms/件 |
| bge-m3 | MIT | 0.895 (0.64) | 0.997 (0.92) | 0.689 (0.40) | 約 50ms/件 |

- キーワードだけの場合の F1 は 生成AI 0.74 / Physical AI 0.96 / 数学 0.86（数学は発信元の指定による一致を含む）。キーワードと組み合わせると 生成AI 0.84 / Physical AI 0.92 / 数学 1.00 になりました。数学の正解は4件だけのため、数学の数値は参考程度です。
- **ライセンス（2026-10-20 に Gemma 利用規約の本文〔2026-04-01 更新〕と禁止用途ポリシーを読んで確認）**: embeddinggemma は定期ジョブの中だけで動かし、モデルそのものは配布せず、利用者に届くのは出力（ベクトル）だけです。規約では出力は派生モデルに含まれず、Google は出力の権利を主張しません（3.3）。このため、有料化しても、モデルの再配布にかかる条件（利用制限の引き継ぎ、規約の写しの同梱）は生じません。守る条件は、禁止用途ポリシーに反しない使い方（分類・照合に使うだけ）と、モデルのタグの固定（`embeddinggemma:300m`）です。**次の場合は再確認します**: ブラウザにモデルを同梱する、他者に API として提供する、別の版（Gemma 4 の新しい規約など）に移る。Apache 2.0 の qwen3-embedding（`EMBEDDING_MODEL=qwen3-embedding:0.6b`、しきい値 0.40）に切り替える手もありますが、評価では精度が下がります。法的な助言ではありません。
- 誤一致の例: 「quant（クオンツ）」の記事が量子技術に、米国の制裁に関する声明がテック政策に一致することがあります。
- プロフィールは `data/profiles/<ID>.json` に保存します（現在は1人分。複数ユーザー化の際はユーザーごとの ID で切り替える想定）。初期設定は `src/profile.ts` の `DEFAULT_PROFILE` です。

## 話題のまとめとブリーフィング
- **話題のまとめ**: 同じ出来事についての発表・報道（例: ノーベル化学賞についての首相官邸と文部科学省の発表、同じ事故の続報、プレスリリースの各言語版）を1枚のカードにまとめ、「関連 ◯件」と発信元を表示します。記事を開くと「関連する発表・報道」から各発信元の記事に移動できます。
  - 判定は、埋め込みベクトルの近さ（0.86 以上）、または近さ 0.72 以上で珍しい語（固有名詞など、記事全体で8件以下にしか出てこない語）を2つ以上共有していること。公開日時の差は96時間以内。生成AIは使いません。
  - 「◯◯国 渡航情報」のように書式が同じで内容が別の発表は、珍しい語の条件でおおむね分けられますが、委員会の開催案内など一部はまとまります（「同じ話題」ではなく「関連」と表示しています）。
  - 埋め込みモデルが使えない場合はまとめません。
- **ブリーフィング**: マイニュースの先頭に、直近24時間の話題から関心トピックが偏らないよう（1トピック2件まで）最大5件を選んで表示します。見出しで一致した記事など、一致の強い話題だけを選びます。週末など5件に満たない場合は48・72時間に広げます。複数の発信元が伝えている話題は上位にします。説明文は要約・発表文の最初の一文をそのまま使います。
- キーワードで一致しても内容がトピックから大きく離れている記事（類似度がしきい値より 0.13 以上低い）は、一致の強さを半分にします。
- 「生成AIが選ぶ◯◯、1位は…（言及率）」のような、AI 検索向けの広告を兼ねた順位調査は取り込みません。

安全保障・文化・芸術・イベントは、上記の情報源に加えて、政府・自治体・研究機関・団体の発表の見出しと説明文に該当する語（防衛、サイバー攻撃、museum、festival など）があれば分類します。企業の発表はセキュリティ製品やイベントの宣伝と区別できないため、この3分野には分類しません。日本の文化・芸術・イベントは、文化庁などが RSS を配信していないため、まだ件数が少ない状態です。

## 品質チェック（`npm run audit`）
起動中のアプリの API を読み、利用者の要望を満たしているかを数値で確かめ、問題を重大な順に並べます（`--samples` でマイニュース上位20件も表示）。改善はこのチェックを実行 → 最も重大な問題を直す → 再実行、の繰り返しで進めています。
- **一次情報**: 報道機関のドメインや、政府・企業・研究機関・団体以外の種類が情報源に含まれていないか
- **情報源の健全性**: 取得エラー、30日間0件（更新が少ないだけか、取り込みの不具合かを区別）、最新記事が古い情報源
- **量**: 選んだ地域・重点分野ごとの直近1週間の件数、関心トピックごとの「強い一致」の件数
- **ブリーフィング**: 5件そろうか、プレスリリース配信サービスに偏っていないか、発信元の重複、説明文の有無
- **要約**: マイニュース上位の記事に説明文・要約があるか

ランキングでは、政府・研究機関・団体の発表を、配信サービス経由の企業発表（宣伝や調査リリースが多い）より上位にし、ブリーフィングに載る配信サービスの発表は1件までにしています。政府の祝日の挨拶、記者会見・発表の予告（実際の発表は別に配信される）は取り込みません。

## 設計方針
- 一覧の説明文（100文字以内）は RSS の説明文をそのまま短縮したもの。要約は発信元の本文のみを根拠に作成し、抜粋か AI による要約かを明示する
- 要約は特定の AI サービスに依存しない。既定は生成AIを使わない抽出型で、必要に応じてオープンソースのモデルや API に差し替えられる
- ハッシュタグは発信元・カテゴリ・地域の事実のみから生成する
- 全文は表示せず、必ず「元記事を読む」から発信元で確認できるようにする。発信元の利用条件が商用の利用・再配布を制限している情報源（15件。[SOURCE_TERMS.md](SOURCE_TERMS.md) の B1）は、見出しと原文へのリンクだけを表示する（`titleOnly`。説明文・要約・画像・本文は出さない）

## 運用メモ
- フィードを追加・変更する場合は `src/newsPipeline.ts` の `officialFeeds` 配列を更新してください。
- フィードは10分間サーバー側でキャッシュします。取得はフィードごとに8秒でタイムアウトします。
- フィードに画像がない記事は、新しいものから順に記事ページの画像（og:image）を裏で確認し、サムネイルに使います（1記事1回のみ。サイト共通のロゴ画像は除外）。
- 取得した記事は `data/news-archive.json` に30日分蓄積します（PR TIMES のように新着の入れ替わりが速いフィードでも、一定期間分を表示するため）。削除すると次回取得分から作り直します。
- PR TIMES・@Press は最新分（数時間分）しか配信しないため、企業の発表はサーバーを起動している間に蓄積されます。停止中に配信された発表は取り込めません。
- 東証の適時開示（TDnet）は robots.txt で自動取得が禁止されているため、取得していません。
- 全フィードの取得に失敗し、蓄積データもない場合のみ「サンプル」バッジ付きの記事を表示します（実在の発表ではありません）。
- 取得に失敗したフィードはサーバーのログに `[feed] 発信元名: 理由` の形式で表示されます。

## 表示言語（多言語対応）
画面は日本語・English・Bahasa Indonesia・Bahasa Melayu・ไทย・Tiếng Việt・Filipino・简体中文・繁體中文・Français・Español・Deutsch・Português に対応しています。初回は保存した選択がなければブラウザの言語設定から決め、対応外の言語なら英語にします。設定画面と初回の質問で切り替えられます。
- 訳は `public/locales/<言語>.json` にあります。日本語の文言をそのままキーにしていて、`en.json` が基準です。情報源の名前は `sources.json` にあり、全言語で共通に使います。
- 訳がない文言は英語、英語もなければ日本語で表示します。件数で形が変わる文言は `{ "one": …, "other": … }` の形で書きます。
- 言語を追加する手順: ① `public/i18n.js` の `LANGUAGES` に言語を足す ② `public/locales/<言語>.json` を作る ③ `npm run check:locales` で抜け・余分なキー・`{置き換え}` の食い違いを確かめる（GitHub Actions でも実行します）。
- **訳は機械的な下訳です。** 公開前に、各言語の母語話者による確認が必要です。
- 母語話者の確認の手順: ① `python3 scripts/review/export_review.py` で言語ごとの確認シート（`review/sivree-review-<言語>.xlsx`、Git には含めない）を作る ② 各シートを母語話者に渡し、行ごとに OK / Needs change と修正を入れてもらう ③ 返ってきたファイルを `python3 scripts/review/import_review.py <ファイル> --dry-run` で確かめてから、`--dry-run` を外して取り込む ④ `npm run check:locales` を実行する。Python と openpyxl が必要です（開発用で、本番の動作には使いません）。
- 翻訳しないもの: 記事の見出し・本文・要約・ブリーフィングの文章（発信元と要約エンジンの言語のまま）、初期トピックのキーワードと説明（照合に使うデータ。英語表示では英語の部分だけを見せ、日本語のキーワードは保持します）、サーバーの動的なエラーメッセージ。
- 未対応: 右から左に書く言語（アラビア語・ペルシア語など）は、`dir` の仕組みだけで、レイアウトの対応は未了です。クメール語・ラオ語・ミャンマー語は未追加です。

## API
- `GET /api/categories` — カテゴリと地域の一覧
- `GET /api/news?category=&subgroup=&sourceType=&keyword=&offset=&limit=`（`subgroup` は地域） — 記事一覧（総件数は `X-Total-Count` ヘッダー）
- `GET /api/news/:id` — 記事、発信元ページから抽出した本文の冒頭、保存済みの要約
- `GET /api/news/:id/summary` — 要約（未作成なら作成して保存）
- `GET /api/config` — 使用中の要約エンジン
- `GET /api/news?forYou=1` — マイニュース（関連度順。各記事に一致した関心トピック `matches` と、まとめた関連記事 `related` を付与）
- `GET /api/briefing` — ブリーフィング（最大5件の話題と、関心トピックごとの話題数）
- `GET /api/filters` — カテゴリ・地域・発信元の種類の一覧
- `GET /api/profile`・`PUT /api/profile`・`POST /api/profile/reset` — 関心プロフィールの取得・保存・初期化

## セキュリティとプライバシー
- **読み込めるものを制限**: `index.html` の Content-Security-Policy で、スクリプト・通信先を自分のサイトのファイルだけに絞っています（インラインのスクリプトとイベント属性は使いません）。`Referrer-Policy` は `no-referrer` です。
- **記事の画像は初期状態でオフ**: 画像は発信元のサーバーから直接読み込まれ、閲覧していることが発信元に伝わるためです。設定の「画像」でオンにできます（端末ごとの設定）。
- **取得元への配慮**: 発信元には `SivreeBot` と名乗り（ブラウザを装いません）、フィードと記事ページの取得前に robots.txt を確認します（`src/robots.ts`）。アクセスを拒むサイトの回避はしません。
- **データは端末内**: 関心プロフィール・非表示にした記事・保存した記事・言語は、この端末のブラウザにだけ保存します。アカウントもサーバー側の利用者データもありません。
- **自動テスト**: `npm run test:xss` は、スクリプトや HTML を含む悪意のある記事データを描画しても、実行できるものが出力されないことを確かめます（公開ワークフローでも実行）。
- **依存関係とビルド**: GitHub Actions は commit に固定し、Dependabot が毎週更新を知らせます。`npm audit` は 0 件です。

## 記事の保存と引用

詳細画面の「保存」で記事を保存し、「引用」で引用を作ります。保存した記事は、画面右上のしおりのアイコンから開きます（`#/saved`）。

- 保存するのは、発信元が付けた見出し・発信元の名前・URL・発表日と、利用者のメモだけです（説明文・要約・画像は持ちません）。プロフィールの `savedItems`（上限 1000 件）に入るので、掲載期間の30日が過ぎても残り、設定のコピーと Google ドライブ同期で端末間に移ります。両方の端末で変更があった競合のときは、どちらの記事も残します。設定を初期化しても、保存した記事は消えません。
- 引用の書式は、出典表記（表示言語に合わせた文）・APA・Markdown・BibTeX・RIS です。保存した記事の一覧からは CSV も書き出せます。コピーとファイル保存ができ、すべてブラウザの中で作ります。メモは CSV と RIS にだけ含めます。
- 見出しは AI の訳ではなく発信元の原題を使い、発表日は発信元の地域（日本・カナダ・米国・欧州）の暦で書きます。閲覧日は引用を作った日です。
- 処理は `public/saved.js`（書式・統合。日本語の文言は持たない）と `public/app.js`（画面）です。`npm run test:saved` で、書式・画面・敵意のある内容・競合時の統合を確認できます。

## 端末間の設定の同期（任意）

設定は端末のブラウザにだけ保存し、Sivree のサーバーには置きません。端末間で揃えたいときは次の方法があります。

- 設定画面の「設定をコピー」「設定を貼り付け」
- 「Google でログインして同期」: 利用者自身の Google ドライブにあるこのアプリ専用の非表示フォルダ（`drive.appdata` のみ）に設定を 1 ファイル置きます。`public/sync.js` が処理し、押すまで Google とは通信しません。

有効にするには Google Cloud でウェブ用の OAuth クライアント ID を作り（無料。承認済みの JavaScript 生成元に配信元のオリジンを追加）、`public/sync.js` の `CLIENT_ID` に設定します。空のあいだは同期の項目は表示されません。`npm run test:sync` で判断ロジックを確認できます。

- 同時更新では、Drive API v2 のファイル ETag と条件付き更新（`If-Match`）で古い内容の上書きを拒否し、最大5回まで再取得・統合します。初回に同名ファイルが複数できた場合は固定のIDを基準に統合し、統合済みのコピーから削除記事が復活しないよう記録します。コピーは復旧用に残し、「ドライブの保存データを削除」でまとめて消せます。
- 通信中の端末内の編集は保持し、まだ送っていない変更は同期済みにしません。未同期・失敗時はヘッダーの同期ボタンと設定画面に状態を表示します。設定画面の保存は、編集した項目だけを最新プロフィールに反映し、同期で届いた保存記事・メモを巻き戻しません。
- 更新を反映した後は、すべての端末で古いページを閉じて開き直してください。古いページの無条件書き込みまでは、新しいページ側だけでは防げません。同じ項目を両端末で別の値に変えた場合は、既存の時刻による優先規則で一方を採用します。
